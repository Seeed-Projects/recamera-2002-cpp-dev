# One-Command Live Delivery Workflow

Use this workflow when the user describes the demo they want in one sentence
and expects "click in and watch". The deliverable is **a clickable LAN URL** —
not a command list, not a six-stage acceptance table.

Example:

```text
User: I want a demo that detects parking-lot lane markings
Final: http://<host-ip>:8090/?token=...
      Page is ready, waiting for the device to stream; the lane-marking detection pipeline is not wired in yet.
```

## When to use this

- The user wants live view, logs, and parameter tuning, and does **not** ask
  for evidence, scoring, acceptance, or knowledge-base records.
- If the user wants `task-quality` / `evaluate_demo` / reproducible evidence,
  follow the 0-13 steps of [demo-output.md](demo-output.md) instead — this
  workflow cannot replace it.
- The two can be chained: look at the live result first, then return to the
  acceptance flow to fill in the evidence.

## Prerequisites

1. The device is reachable (`probe_device`, or at least SSH port 22
   reachable), with `RECAMERA_PASSWORD` set or an SSH key configured.
2. The demo workspace has the `live` section in `demo.json` (generated by
   `new_demo --live udp`).
3. **The camera/detection code is implemented**: `src/main.cpp` is no longer
   the placeholder idle loop; it can send H.264 via `send_access_unit/send_nal`
   and send results via `send_meta` or `send_annotations_json`. After
   implementing, set `live.implemented` to `true`.
4. For lane-marking/polyline tasks, the demo must send `annotations`
   (polylines) — the UI does not compute lines by itself.

## Steps

### 1. Judge feasibility

Give a verdict per [capability-routing.md](../references/capability-routing.md):

- **Supported**: device, model/algorithm, and inputs all confirmed.
- **Supported with preconditions**: the code path exists, but the
  device/accuracy is unverified.
- **Blocked**: missing hardware, missing model, missing credentials. Name the
  blocking point explicitly; do not fabricate a URL.

### 2. Pick or create the workspace

For an already-implemented live demo: use it directly.

For a new one:

```bash
python3 scripts/new_demo.py --name <slug> --task <task> --live udp \
  --out ~/reCamera_demo
```

Then replace the placeholder loop in `src/main.cpp` using the wiring described
in [tools/sdk.md](../references/tools/sdk.md) and `templates/live/README.md`:

- `camera->init(0)` to get 1920×1080@30 H.264;
- a raw channel at 640×640 for inference;
- video thread: `retrieveFrame(MA_PIXEL_FORMAT_H264)` → `send_nal`;
- inference thread → `send_meta`;
- lane markings → `send_annotations_json` (polylines);
- evidence snapshots → JPEG channel → `send_snapshot`.

Do not set `live.implemented` to `true` unless you actually replaced it.

### 3. Offline chain

```bash
python3 scripts/validate_demo.py --demo-dir <dir>
python3 scripts/build_demo.py    --demo-dir <dir>
python3 scripts/smoke_demo.py    --demo-dir <dir>
```

`launch_demo.py` also runs these automatically (can be skipped). If the build
fails, do not proceed to deployment.

### 4. One-command deploy + UI

```bash
python3 scripts/launch_demo.py --demo-dir <dir> \
  --host 192.168.42.1 --bind 0.0.0.0 --allow-actions --allow-service-stop
```

It will:

- start `serve_demo.py` in the background (detached — keeps running after the
  terminal exits);
- pick the host NIC address based on the route to the device and inject
  `--peer` via `LIVE_PEER`;
- `probe → install --replace → start`; Node-RED / Supervisor are stopped only
  with an explicit `--allow-service-stop` (restorable after testing);
- wait for the first frame, write `dist/live/server.json` / `launch.json`;
- then collect `live.perf` samples for `--perf-wait` seconds and emit
  `LIVE_RESULT_AGE_MS` / `LIVE_DETECT_FPS` /
  `LIVE_PERF=ok|degraded|unmeasured`;
- output `LIVE_URL=`.

### 5. Read the status

| Status | Reply |
|---|---|
| `ready` | Page is ready and the device is streaming; if there are real detections, state what is detected. |
| `placeholder` | Page is ready, but the camera/detection pipeline is still the skeleton — only logs are viewable; do not claim detections are visible. |
| `degraded` | Page is ready, but deployment failed, there is no video, or `LIVE_PERF=degraded` (result age/update rate below target); give the log location and the next step. |
| `reused` | Reused an already-running service; same URL. |

When the port is taken, `launch_demo` automatically switches the host UDP port
and notifies the device via `LIVE_ARGS`; after changing the `live.udp` ports in
`demo.json`, launching again restarts the host service, and with
`--no-deploy` the device must be restarted manually to use the new port.
To stop:

```bash
python3 scripts/launch_demo.py --demo-dir <dir> --stop
```

`--stop` stops only the host service, not the device demo.

When `LIVE_PERF=degraded` you must not say "performance is acceptable". Check
`LIVE_WARNING=perf ...` and the UI's "result age" first: a large result age is
usually not a slow model but the inference thread calling `retrieveFrame`
directly and stepping on the FIFO queue (depth = channel fps, takes the
oldest frame, drops new ones when full). Switch to `FrameRelay` from
`live_camera.hpp` per [tools/device-pipeline.md](../references/tools/device-pipeline.md),
and set the CH0 fps to the consumption rate.

## Reply contract

The last user-facing message, in fixed order:

1. **One clickable URL line** (the literal `LIVE_URL`, token included).
2. **At most two status lines**, for example:
   - `Page is ready, waiting for the device to stream.`
   - `The device is streaming; detection boxes are not wired to a model yet (placeholder).`
   - `Live detection in progress: <class/task>.`
   - `Lane-marking overlay is wired in; quality has not been evaluated on fixed inputs.`
3. Optionally one next-step sentence: use `capture_evidence.py --source live`
   to keep evidence; use `workflows/demo-output.md` for acceptance.

Forbidden:

- Claiming the demo is done / detection works / quality meets the bar just
  because "the URL opens".
- Giving accuracy, recall, F1, or quality conclusions without running
  `evaluate_demo.py`.
- Delivering a command list as the deliverable — the user wants the URL.
- Treating the live view as evidence; it is neither `device-run` nor
  `task-quality`.

## Lane-marking / parking-lot example

"Parking-lot lane-marking detection" is not a built-in recipe:

- If the existing demo only does **directional-arrow ROI classification**,
  that is not lane-marking detection;
- lane markings need a model (ONNX→cvimodel — the current TPU-MLIR environment
  is unverified) or classic CV;
- the UI already supports polylines/polygons; the demo computes the lines and
  sends `annotations`;
- with no algorithm, report `placeholder`/`degraded` — do not pass detection
  boxes off as lane markings.

## Common failures

| Symptom | What to do |
|---|---|
| No `LIVE_URL` | Check `dist/live/server.log`; port/bind/token issues |
| `degraded` + probe failed | Device unreachable/password/key; fix the network first |
| `degraded` + install failed | Check the `deploy_demo` output; disk/permissions/artifact architecture |
| Service healthy but no video | The demo is not sending H.264; check whether `src/main.cpp` still has the placeholder loop |
| Video but no boxes/lines | `meta`/`annotations` not sent; or the `preprocess`/coordinate space is wrong |
| `placeholder` | `live.implemented` not set to true, or the camera pipeline not wired |
