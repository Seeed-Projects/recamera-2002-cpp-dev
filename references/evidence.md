# Evidence specification

The goal of evidence is to let another person re-verify your work **without watching your session**: which device was used, which version, which file, which command, what the output was, and which step was not done.

## 1. Evidence levels

| Level | Produced by | May claim | Must not claim |
|---|---|---|---|
| `static` | `validate_demo.py` | Contract/structure/hash correctness | Compiles, runs |
| `offline` | `build_demo.py` | Artifact is a RISC-V ELF with fixed hashes | The device can load it |
| `host-baseline` | Official Python/NVIDIA scripts | Baseline results on the fixed inputs | Device behavior |
| `device-upload` | `deploy_demo.py --action upload/install` | Files arrived with matching hashes | Process started |
| `device-run` | `deploy_demo.py --action start/verify` | Process/logs/markers match | Accuracy, recall |
| `task-quality` | `evaluate_demo.py` | Quality-gate conclusion on fixed inputs | Generalization, real-time performance |

In reports, mark each item as executed / not executed / unverified; never substitute lower-level evidence for a higher level.

## 2. Directory structure

```text
~/reCamera_demo/<demo_name>/
├── demo.json
├── src/                      # source code
├── models/                   # models (document separately if not committed to Git)
├── dist/
│   ├── <binary>
│   ├── build-report.json
│   ├── device/<action>-report.json
│   └── device/logs/
├── eval/
│   ├── input/{images,video,manifest.json}
│   ├── baseline/{baseline.jsonl,baseline.mp4,frames/,visualized/}
│   ├── recamera/{recamera.jsonl,recamera.mp4,frames/,visualized/}
│   ├── recamera/evidence/{evidence.json,capture.mp4,frame.jpg,webui.png,webui.html}
│   ├── live/<timestamp>/{session.json,events.jsonl,logs/device.log,frames/*.jpg}
│   ├── qa_report.json
│   ├── qa_report.md
│   └── failures.json
└── DEPLOY_REPORT.md
```

On the device:

```text
/userdata/demos/<demo_name>/
├── <binary>
├── demo.json
├── run.pid
└── logs/run-<timestamp>.log
```

The staging directory is `/userdata/.demo-stage/<demo_name>-<timestamp>`; installation verifies the SHA-256 of every file.

## 3. evidence.json

`capture_evidence.py` generates:

```json
{
  "schema_version": 1,
  "kind": "demo-evidence",
  "generated_at": "<ISO-8601 timestamp>",
  "source": "rtsp",
  "target": "rtsp://192.168.42.1:554/live",
  "duration_s": 20,
  "tool_versions": {"ffmpeg": "ffmpeg version ..."},
  "artifacts": [{"path": "capture.mp4", "size": 123456, "sha256": "..."}],
  "checks": [{"name": "rtsp.video", "ok": true, "detail": "ffmpeg rc=0"}],
  "device": {"hostname": "reCamera", "arch": "riscv64", "api_raw": "..."},
  "device_contract_drift": [],
  "ok": true
}
```

Requirements:

- Every artifact is non-zero bytes and carries a hash.
- Video must be playable and screenshots must clearly show the OSD/detection boxes; logs alone do not count as visual evidence.
- Capture Web UI evidence with `--source webui` (headless Chrome screenshot + DOM); don't photograph the screen with a phone.
- For UDP demos use the official `udp_receiver.py`, passed via `--receiver`; only frames saved by the receiver count as evidence.
- The host-side live view is not evidence by itself; convert it with `--source live --session <dir>`. This mode
  requires at least one device JPEG snapshot, the device log, the event stream, and `session.json` —
  missing any one fails. The `source` field in `evidence.json` is `live`, and artifacts are named
  `live-*.jpg` / `live-device.log`.

## 4. Device run reports

`deploy_demo.py` writes `dist/device/<action>-report.json` for every action:

```json
{
  "schema_version": 1,
  "kind": "demo-deploy",
  "action": "verify",
  "generated_at": "...",
  "demo": "hello_cpp",
  "target": {"host": "192.168.42.1", "user": "recamera", "port": 22},
  "remote_dir": "/userdata/demos/hello_cpp",
  "files": [{"path": "hello_cpp", "size": 123, "sha256": "..."}],
  "checks": [{"name": "verify.markers", "ok": true, "detail": "..."}],
  "payload": {"ok": true, "running": true, "evidence_level": "device-run"},
  "ok": true
}
```

Passwords, tokens, and `sshpass` command lines never appear in reports; `probe_device.py` redacts raw output.

## 5. DEPLOY_REPORT.md

Generated by `record_demo.py --report-dir`, containing:

- Date, status, capability, model files, dependencies, build issues, verification, lessons, wiki issues.
- Evidence JSON (if any).
- An evidence-boundary statement: device/hardware/quality-gate items not executed.

## 6. Report wording

- "Device verified" may only be used when upload + install + start + verify were actually executed.
- When only a PID/socket exists, write "process present, task correctness unverified".
- Without device access, write "device acceptance not executed" and deliver the completed offline artifacts.
- For missing hardware (gimbal, reSpeaker, Jetson, Meshtastic) write `blocked`; don't report "hardware missing" as a "wiki failure".
