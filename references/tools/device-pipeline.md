# Device-side camera pipeline (the heart of a live demo)

`templates/live/` only provides UDP transport, the parameter listener, and the host smoke test; **it does not open the camera**.
The `src/main.cpp` generated by `new_demo.py --live udp` is a placeholder idle loop,
`demo.json` sets `live.implemented=false`, and the UI shows "demo skeleton".

To get actual camera footage into the URL, you must add a `camera_pipeline.cpp/.h` and
build it in a mode that can link SSCMA. This document records verified SDK facts and the recommended wiring.

## Read this first: the frame queue turns "slow" into "old" (measured on reCamera 2002)

`ma::Camera` uses a per-channel FIFO queue whose depth equals that channel's fps; when it is full it blocks for one frame
interval and then drops the **new** frame:

- `new MessageBox(param.fps)` (`ma_camera_sg200x.cpp:243`)
- `fetch()` reads `m_mbox.r`, i.e. the oldest frame (`ma_osal_pthread.cpp:437`)
- When `post()` is full it calls `pthread_cond_timedwait`; after the timeout the caller deletes the new frame
  (`ma_osal_pthread.cpp:462`, `ma_camera_sg200x.cpp:121`)

So calling `retrieveFrame` directly inside the inference loop means a slow consumer reads stale frames. Same
binary, same scene, measured:

| CH0 | Decode time | Detection fps | Result age avg / max |
|---|---|---|---|
| 15 fps | 207–222 ms | 5.0–5.2 fps | 2.91–2.99 s / 3.09–3.24 s |
| 5 fps | 163–182 ms | 4.2–4.4 fps | 0.078–0.201 s / 0.18–0.67 s |

Frame age was verified via `ma_img_t::timestamp`: it is `Tick::current()` truncated to a uint32
in nanoseconds, so `(uint32_t)Tick::current() - frame.timestamp` is the true age within 4.29 s.
After idling 1 s the first frame measured 1019 ms, then frames taken every 0.5 s measured 1466/1917/2367/2816 ms —
the queue hands out ever-older frames while new ones are dropped.

**Correct wiring**: use `FrameRelay` from `templates/live/src/live_camera.hpp` (`--live udp`
copies it into `src/`):

```cpp
recamera_live::FrameRelay relay;
relay.start(camera, MA_PIXEL_FORMAT_RGB888);   // separate thread keeps fetching frames, retains only the latest

recamera_live::LatestFrame f;
while (running) {
    if (!relay.wait(f, 1000)) continue;        // wait for the next new frame
    detector->run(f.img.data, f.img.width, f.img.height);
    camera->returnFrame(f.img);                // the consumer is responsible for returning it
    const int age_ms = f.age_ms + recamera_live::now_ms() - f.acquired_ms;
    recamera_live::send_meta(..., f.acquired_ms, age_ms);
}
```

- Set CH0's fps to **the rate the consumer can actually sustain**: 5–8 for CPU decoding, 10–15 for NPU inference.
  Setting 15 will not make the model faster; on a single core it instead drags decoding from ~200 ms out to 550–765 ms.
- The video channel (CH2) can still use `retrieveFrame` directly, but the video thread must keep up with the encoder
  and must not drop NALs; the "retain only the latest" strategy does not apply there.
- `send_meta`'s `frame_ts_ms`/`age_ms` feed the UI's "result age" and the performance gate.

## Three channels

`ma::Camera` on SG200X has exactly three channels:

| Channel | Enum | Format | Purpose |
|---|---|---|---|
| 0 | `CHN_RAW` | RGB888 | 640×640 inference (VPSS, no VENC) |
| 1 | `CHN_JPEG` | JPEG | evidence snapshots (low fps) |
| 2 | `CHN_H264` | H.264 | 1080p30 video (hardware VENC) |

`camera->init(0)` selects preset 0 = 1920×1080@30 and pre-configures the H264 channel;
`commandCtrl(kChannel, kWrite, n)` is what actually enables the channel.
`retrieveFrame(frame, MA_PIXEL_FORMAT_H264)` returns **one VENC pack**;
`frame.count`/`frame.index`/`frame.key` are used for `send_nal` grouping.
An empty queue returns `MA_AGAIN`; a disabled channel returns `MA_EPERM`.

## Initialization order

```cpp
auto* camera = /* the Camera from Device::getInstance()->getSensors() */;
camera->init(0);                       // H264 1080p30 preset

ma::Camera::CtrlValue val;
val.i32 = 0;                           // CH0 inference
camera->commandCtrl(ma::Camera::CtrlType::kChannel, ma::Camera::CtrlMode::kWrite, val);
val.u16s[0] = 640; val.u16s[1] = 640;
camera->commandCtrl(ma::Camera::CtrlType::kWindow, ma::Camera::CtrlMode::kWrite, val);
val.i32 = 5;                           // inference cadence: set to the actual consume rate, do not default to 15
camera->commandCtrl(ma::Camera::CtrlType::kFps, ma::Camera::CtrlMode::kWrite, val);
val.i32 = 0;                           // kPhysical=0: copy, avoids VB reclaim races
camera->commandCtrl(ma::Camera::CtrlType::kPhysical, ma::Camera::CtrlMode::kWrite, val);

val.i32 = 1;                           // CH1 JPEG
camera->commandCtrl(ma::Camera::CtrlType::kChannel, ma::Camera::CtrlMode::kWrite, val);
val.u16s[0] = 640; val.u16s[1] = 480;
camera->commandCtrl(ma::Camera::CtrlType::kWindow, ma::Camera::CtrlMode::kWrite, val);
val.i32 = 5;
camera->commandCtrl(ma::Camera::CtrlType::kFps, ma::Camera::CtrlMode::kWrite, val);
val.i32 = MA_PIXEL_FORMAT_JPEG;
camera->commandCtrl(ma::Camera::CtrlType::kFormat, ma::Camera::CtrlMode::kWrite, val);

val.i32 = 2;                           // CH2 H264; size/fps use preset 0
camera->commandCtrl(ma::Camera::CtrlType::kChannel, ma::Camera::CtrlMode::kWrite, val);

camera->startStream(ma::Camera::StreamMode::kRefreshOnReturn);
```

Three threads:

- **Video**: `retrieveFrame(H264)` → skip non-key packs until the first keyframe →
  `send_nal(frame.data, frame.size, frame.index, frame.count, frame.key, now_ms())`
  → `returnFrame`; sleep 1 ms on `MA_AGAIN`.
- **Inference**: `FrameRelay` (`live_camera.hpp`) continuously fetches RGB888 and retains only the latest →
  `relay.wait(f)` → `engine->setInput` → `detector->run` →
  `returnFrame(f.img)` → `send_meta(..., f.acquired_ms, age_ms)`;
  read thresholds from `recamera_live::params()` before each frame.
  Do **not** call `retrieveFrame` directly in the inference loop (see the previous section).
  SSCMA bboxes are already normalized center + normalized width/height; convert them straight into `Detection[]`.
- **Snapshot**: JPEG channel → `send_snapshot(..., 1fps)`; evidence capture needs at least one.

## Pitfalls you must respect

1. **Do not casually call `initVideo()`**. `setupVideo()` discards the caller's size/encoding for CH1/CH2
   and uses the MAIN_* settings from `/userdata/local/camera.conf` instead; `setVideoBitrate()` is also overridden by conf.
   If you must call `initVideo()`, immediately read back the real values with
   `getVideoEffectiveConfig(VIDEO_CH2, &p, &bitrate)`, write them into `recamera_live::Config`, and
   `send_log("error", ...)` then exit when `p.format != VIDEO_FORMAT_H264` (jmuxer only supports AVC).
2. **`kPhysical=0`**. In physical mode (`kPhysical=1`) VPSS frames are released with `CVI_VPSS_ReleaseChnFrame`
   immediately after the callback returns; cross-thread inference would read a reclaimed VB buffer — the symptom is
   intermittent garbage boxes/crashes. Copy mode costs ~1.2 MB/frame extra but is safe.
3. **`force_idr` must actually call `requestVideoIDR(VIDEO_CH2)`**. `live_udp` is
   SDK-free and can only consume `force_keyframe_requested()` in the camera TU.
4. **`Config.video_width/height/fps` must equal the actual VENC output**; the `LIVE_STATUS`
   UI cannot probe them automatically.
5. **Service arbitration**: `runtime.services_stop` stops `S03node-red`/`S91sscma-node`/
   `S93sscma-supervisor`, with `--allow-service-stop`; restore them after testing. When the camera is occupied,
   `retrieveFrame` keeps failing.
6. **Runtime libraries**: SDK-linked artifacts need
   `LD_LIBRARY_PATH=/mnt/system/lib:/mnt/system/usr/lib:/mnt/system/usr/lib/3rd`;
   the `templates/live` manifest already sets this in the runtime_env of `device-contract.json`.
7. **Inference queue**: the CH0 queue depth equals the channel fps, FIFO takes the oldest, and a full queue drops
   new frames. A slow consumer that fetches frames directly will see pictures from seconds earlier (measured: 15 fps
   channel / 5 fps consumer = 2.9–3.2 s). Use `FrameRelay`, set CH0 fps to the consume rate, and report `age_ms`
   honestly; the performance gate uses it to decide whether the demo passes — "the process is up" is not a substitute.

## Build

`ma::Camera` / `EngineCVI` need the full SDK:

- `SG200X_SDK_PATH` (pointing at your `sg2002_recamera_emmc` checkout, e.g.
  `export SG200X_SDK_PATH=/path/to/sg2002_recamera_emmc`);
- the Xuantie RISC-V musl toolchain;
- the SDK's `cmake/project.cmake` solution layout: root `CMakeLists.txt` +
  `main/CMakeLists.txt`, with `component_register(... PRIVATE_REQUIREDS sscma-micro sophgo)`.

Currently `build_demo.py`'s `cpp`/`cmake` modes only suit SDK-free host smoke builds;
a demo that really links the SDK should be built with its CMake inside the SDK tree, or a future
`build.kind: sdk-solution` could be added. **This is a Linux-host capability**; Windows/macOS can still run
the `serve_demo.py` host-side viewer, but cannot cross-compile SDK demos.

Keep host smoke and SDK code in separate files: `main.cpp` + `live_udp.cpp` must stay host-compilable,
`camera_pipeline.cpp/.h` is added only in SDK builds; `smoke.sh` does not compile it.

## Three levels of lane marking detection (honest grading)

| Level | Approach | Feasibility |
|---|---|---|
| 1 | Live 1080p video + YOLO detection boxes + user-drawn line ROI/rules | **implementable now**, without claiming a lane model |
| 2 | On-device OpenCV classic CV: downsampled grayscale → trapezoid ROI → Canny/row peaks → sliding-window fit → `shapes` polyline | feasible (SeSg OpenCV already exists), needs measured fps |
| 3 | Train a lane model → ONNX → cvimodel → device evaluation | **Blocked**: no official lane model/dataset, TPU-MLIR environment unverified |

Until levels 2/3 actually produce geometry, keep `live.implemented` at `false` and `LIVE_STATUS`
at `placeholder`; do not write "lane detection succeeded" in reports.

## Measured pitfalls (QR-code demo, reCamera 2002)

1. **Studio grabs the camera**. After `S93sscma-supervisor` starts it brings up apps like `K92yolo-detector`
   and monopolizes VI. Stopping only the three init scripts in `runtime.services_stop` is not enough:
   you get `CVI_VPSS_CreateGrp failed` / `startVideo failed 0xc00e8004`. First run
   `S93sscma-supervisor stop` (it stops the apps along with it), then confirm `ps w | grep yolo26` is empty.
2. **Never `kill -9`**. CVI's VB/VPSS state stays in the kernel and the next start reports
   `0xc0068004`; only a reboot recovers. SIGTERM exits cleanly within 300 ms and releases everything.
3. **VPSS rejects two output channels with the same size but different pixel formats**. When CH0 RGB888 and CH1 JPEG both
   use 640×360, VI still receives frames but VPSS `SendOK=0`, `vb_pool` fills up, and the whole pipeline
   silently stalls (no stdout error). Changing CH1 to 640×480 restored it. After any channel resolution change,
   check `SendOK` in `/proc/cvitek/vpss`.
4. **Do not upscale the whole frame 2× before quirc**. 960×540→1920×1080 costs about 440 ms per call (single core)
   and starves the scanning thread; only enlarge the center ROI.
5. **`deploy_demo.py --action stop` may report alive**. It waits only 1 s after signaling; on a single core a normal
   exit takes ~300 ms, but if a previous failed startup left an already-exited pidfile, it misreports.
   Confirm with `ps w` and, if needed, `kill` by PID (never `-9`).

6. **When recognition distance falls short, check blur and quiet zones before raising resolution**. Measured on real
   camera frames with a +0.9px Gaussian blur added to the background: at 2px/module (50px symbol) and 960×540 the old
   gradients all fail; adding one unsharp pass (3x3, k=12, +12ms) makes it readable, roughly ×1.5–2 recognition distance.
   Raising the scan resolution from 960 to 1280 only buys ×1.33 while the per-frame cost goes ×1.7 (237→473ms; even
   worse at 1080p). Also: **a code without a quiet zone cannot be read by any decoder** (quirc relies on the quiet zone
   to locate the boundaries) — that is a label design problem; add a 2-module white border, no code can compensate.

## Verification markers

After completing the camera TU, write the following stdout/`send_log` markers into
`runtime.expect_stdout` so `deploy_demo verify` can prove the video path actually started:

```text
live: camera ch2=1920x1080@30
live: video fps=... kbps=... dets=...
```

`live: started` alone does not prove there is a video feed.
